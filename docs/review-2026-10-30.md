# Approved-project review and remediation — 30 October 2026

## Findings

| Severity | Flaw | Consequence | Remediation |
| --- | --- | --- | --- |
| Critical | Profile validation required the SHA-256 of a retired two-line Python/NumPy marker, while E2B and Oracle builders produce a versioned installed-package inventory. | New template hashes were rejected at submission; the retired hash passed submission but failed the sandbox's live lock check. No newly built environment could complete approval. | Validation accepts the operator-supplied 64-character lock digest. Each sandbox checks its live installed-package inventory against the approved digest before source transfer. Tests use a representative v2 inventory hash rather than deriving their expectation from the retired production helper. |
| High | Profile approval recorded a sample-validation commit, but later run admission accepted a different source snapshot from the same repository. | Code never covered by the operator's sample validation could run under the old approval. | Approval now stores the validated source snapshot digest from the completed validation job. The API admission path compares the new PR base snapshot against it, and the separate worker repeats the check against its immutable job spec. Private replay export also checks the binding. |
| Medium | Sample validation ran once per environment and set `sample_validated` without checking stability. | A nondeterministic sample could authorize a profile. | Validation runs the sample twice in each pinned environment, checks conclusions, numeric tolerance, and required dtype consistency, and rejects unstable results. Approval requires the repeatability evidence. |

## Migration and scope

New E2B templates and Oracle images must be built with the versioned lock inventory. Record the builder's actual image or template IDs and lock digests in the validation request. A digest cannot be calculated from the NumPy version alone.

Previously approved profiles do not contain `validated_source_sha256`. They cannot start a new approved-project run or export a previously completed private replay bundle under the new binding rule. Create a new profile version, validate its intended source commit in the prepared environments, and approve that version. An application-code change to the base snapshot likewise needs a new validation and approval. A dependency-only PR whose base snapshot is byte-identical to the validated source remains eligible.

The validation remains a bounded preapproval check, not a proof of scientific correctness. It does not establish a causal mechanism, validate arbitrary dependency graphs, or make the Docker backend a security boundary equivalent to an E2B microVM. Live E2B and Oracle execution still require operator verification.

## Verification

Regression tests cover a v2 lock digest, malformed digests, unstable repeated output, approved-source mismatch at API admission and worker execution, and persistence of the validated source digest. In the project Python 3.12 environment, `python -m pytest tests -q` passed with 662 passed and 19 skipped; `node --test tests/frontend/*.cjs` passed all 22 checks; `python -m ruff check app runner tests` and `git diff --check` passed. The skipped tests include database-backed cases unavailable on this host. Live E2B, Oracle, and hosted deployments were not exercised.
